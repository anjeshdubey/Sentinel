Sentinel — Architecture

An LLM agent that does an on-call engineer's first five minutes of triage automatically — turning a raw alert into a structured, evidence-backed diagnosis before a human opens their laptop.

← Back to live demo

The Problem

When an alert fires, every on-call engineer asks the same three questions: What broke? Who owns it? Has this happened before? Answering them means checking a service catalog, a deploy log, and scattered runbooks — under pressure, by hand. PagerDuty and Datadog route alerts to a human; none of them do that first-pass reasoning. That gap is where slow MTTR comes from.

What Sentinel Does

  1. Normalizes alerts from any source (PagerDuty, Grafana, Datadog, freeform Slack)
  2. Enriches with ground-truth context — service owner, recent deploys — via tool-calling into a system of record
  3. Retrieves matching runbooks and past incidents via RAG, so answers are grounded in real precedent, not the model's memory
  4. Reasons over all of it with Claude, producing a schema-validated diagnosis: severity, root cause, blast radius, confidence, recommended action
  5. Streams the reasoning trace live — every tool call and retrieval is visible, not just the final answer, so the system is auditable rather than a black box

Why These Choices

  • Structured over free text — downstream paging/dashboard systems need a reliable schema, not prose to re-parse under stress.
  • RAG over fine-tuning — runbooks change constantly; retrieval keeps the knowledge base current without retraining, and every claim traces to a source document.
  • Tool-calling over hallucination — service ownership and deploy history come from a real system of record, not model guesswork.
  • Raw SDK over a framework — the tool-calling loop and structured-output parsing are hand-built, to demonstrate the underlying mechanics rather than lean on abstractions.
